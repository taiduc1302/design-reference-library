## Purpose and boundaries

- Inventory **82 public upstream repositories**, including forks and archived examples, against reusable capability areas rather than exposing private local repositories.
- `HIGH` = examine soon; `MEDIUM` = useful when a matching need appears; `LOW` = peripheral inspiration; `NONE` = no current use case. These are research priorities, **not adoption statuses**.
- `RESEARCH_LEAD` means metadata and selected README/source observations only. File-level licensing, security dependencies, maintenance, regression, and operating-system behavior are **not verified**.
- Do not automatically install remote skills, run third-party hooks, connect accounts, copy media/logo/voices, or add cloud dependencies.
- Do not publish private repository paths, tender packages, client names, tokens, personal/family information, or internal screenshots.
- Prefer a small isolated experiment, clear pass/fail checks and manual review before any change to an application.

## Highest-value follow-up experiments

1. **Tender/document lifecycle:** study `chanmeng-slack-waterline` state transitions and test a synthetic cumulative-addendum fixture where every requirement has intake, extraction, review and evidence receipts. Never mark review complete based on a successful fetch.
2. **Civil geometry:** study `archlang` separately from its 3D package; write a small synthetic utility/trench example with explicit units, source geometry and numeric comparisons. Architectural lint is not earthwork volume validation.
3. **Web accessibility:** pilot `a11y-loop` on fictional demo UI at narrow and desktop sizes, keyboard and state variations; compare with a second checker and retain manual checklist.
4. **Agent evaluation:** adapt `chanmeng-ai-product-manager` launch gates to synthetic agent traces and explicit human approval boundaries.
5. **Public previews:** produce reproducible screenshots using `chanmeng-readme-showcase` only after local browser QA and content sanitization.

## Acceptance workflow

1. Capture a source commit SHA and review the actual code-level license and third-party media notices before copying anything.
2. Record dependency, installation side effects, network access, secrets, data exposure and platform compatibility.
3. Write a scoped hypothesis and synthetic test fixture. Do not integrate into another repository directly from this inventory.
4. Run existing local tests, narrow desktop/browser QA where relevant, and compare an independent reference or baseline.
5. Log a reviewer decision (`REJECT`, `HOLD`, `PROTOTYPE`, or `ADOPT`) with evidence link and date. `ADOPT` requires project-specific QA.

## Upkeep

- Re-check upstream archive/fork/license/maintenance status before each experiment. The snapshot date is not ongoing verification.
- Keep the JSON inventory canonical and regenerate this readable table if records change.
- New author collections belong in separate inventory files; do not mix unvetted research leads into `catalog/references.json`, which follows stricter visual curation states.
